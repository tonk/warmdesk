== Installation

For full build-from-source and quick-start instructions see link:../INSTALL.md[INSTALL.md].
This guide assumes the binary is already running and focuses on configuration and operations.

=== Requirements at runtime

[cols="1,3", options="header"]
|===
|Component |Minimum

|OS
|Linux, macOS, or Windows

|CPU
|1 core

|RAM
|128 MB (SQLite) / 256 MB (PostgreSQL / MySQL)

|Disk
|50 MB for the binary + your database and uploaded files

|Network
|Outbound SMTP (optional); inbound HTTP on your chosen port

== Configuration Reference

Configuration is loaded in priority order (highest wins):

. CLI flag `--config /path/to/file.yaml`
. Environment variable `CONFIG_FILE=/path/to/file.yaml`
. `warmdesk.yaml` in the current working directory
. Built-in defaults

Every YAML key has a matching environment variable.
Environment variables always override the YAML file.

=== Full configuration reference

[source,yaml]
----
# Server
port: 8080
# PORT — HTTP listen port

base_url: "https://desk.example.com"
# BASE_URL — public URL; sets Swagger UI host

allowed_origins: "https://app.example.com"
# ALLOWED_ORIGINS — CORS origins

trusted_proxies: ""
# TRUSTED_PROXIES — comma-separated CIDRs/IPs to trust proxy headers from
# Leave empty to trust no proxy (see Reverse Proxy below)

# Security
jwt_secret: "change-me-in-production"
# JWT_SECRET — HS256 signing key
# Generate: openssl rand -hex 32

# Web assets
web_dir: "./web"
# WEB_DIR — compiled frontend (required in prod)

# Database
db_driver: "sqlite"
# DB_DRIVER — sqlite | postgres | mysql

db_dsn: "./warmdesk.db"
# DB_DSN — file path or connection string

db_log: "info"
# DB_LOG — silent | error | warn | info (default: info)

# File uploads
upload_dir: "./uploads"
# UPLOAD_DIR — where attachments are stored

max_upload_mb: 25
# MAX_UPLOAD_MB — per-file upload limit

# Group video calls (optional, LiveKit SFU)
livekit_url: "wss://livekit.example.com"
# LIVEKIT_URL — LiveKit websocket URL

livekit_api_key: "APIxxxxxxxxxxxxxxxx"
# LIVEKIT_API_KEY — server API key

livekit_api_secret: "your-secret"
# LIVEKIT_API_SECRET — matching secret

livekit_room_prefix: ""
# LIVEKIT_ROOM_PREFIX — optional prefix for LiveKit room names,
# useful when multiple WarmDesk instances share one LiveKit server

# TURN server for 1:1 calls (optional, strongly recommended for anything
# but a local LAN)
turn_urls: "turn:turn.example.com:3478"
# TURN_URLS — comma-separated TURN/TURNS URIs

turn_username: "warmdesk"
# TURN_USERNAME — static username configured on the TURN server

turn_credential: "your-secret"
# TURN_CREDENTIAL — matching password/credential

# Logging
gin_mode: "release"
# GIN_MODE — debug | release

api_log: true
# API_LOG — log every HTTP request (default: true)

# Redis (optional — horizontal scaling)
redis_url: ""
# REDIS_URL — e.g. redis://localhost:6379
# Leave empty to use in-process pub/sub

# Locale defaults (overridden per user)
default_locale: "en"
# DEFAULT_LOCALE — en | nl | de | fr | es | da | sv |
# nb | fi | is | pt | it

# Application mode (optional)
# app_mode: "timetracking"
# APP_MODE — leave empty for full WarmDesk; set to "timetracking" for
# a time-tracking-only deployment (see below).

# Instance mode (optional)
# instance_mode: "test"
# INSTANCE_MODE — leave empty for production; set to "test" to serve
# test-branded logos (see below).
----

=== Time-tracking-only mode

Set `app_mode: "timetracking"` (or pass `--mode=timetracking` on the command line, or set `APP_MODE=timetracking` as an environment variable) to run WarmDesk as a dedicated time-tracking server.

Effects:

* Board, chat, topic, and helpdesk API routes are disabled — only time tracking and user management remain active.
* The time-tracking logos (clock-on-desk) replace the default WarmDesk logos everywhere: the web interface, the login screen, and exported PDFs (when no custom company logo is configured in Admin → Branding).
* The `/api/v1/version` endpoint returns `"app_mode": "timetracking"` so clients can detect the mode.

The CLI flag takes precedence over the YAML key, which takes precedence over the environment variable.

=== Test instance branding

Set `instance_mode: "test"` (or pass `--instance-mode=test` on the command line, or set `INSTANCE_MODE=test` as an environment variable) to mark a deployment as a test or staging instance.

Effects:

* The logo variants switch to an orange palette with a "TEST" corner ribbon everywhere: the web interface, the login screen, and exported PDFs (when no custom company logo is configured in Admin → Branding).
* Combines independently with `app_mode` — a `timetracking` instance with `instance_mode: "test"` serves the orange time-tracking logo, not the orange full-WarmDesk logo.
* The `/api/v1/version` endpoint returns `"instance_mode": "test"` so clients can detect the mode.
* The desktop app's system tray icon also turns orange, with "(TEST)" appended to its title/tooltip, whenever it is connected to a test-instance server.

The CLI flag takes precedence over the YAML key, which takes precedence over the environment variable.

=== Generating a strong JWT secret

[source,bash]
----
openssl rand -hex 32
# or
python3 -c "import secrets; print(secrets.token_hex(32))"
----

IMPORTANT: Never use the built-in default `change-me-in-production` in any environment that is accessible from a network.

== Database Setup

=== SQLite (default — recommended for single-server installs)

No setup needed.
WarmDesk creates the file automatically.

[source,yaml]
----
db_driver: sqlite
db_dsn: /var/lib/warmdesk/warmdesk.db
----

Ensure the directory is writable by the process user and is on a volume that is included in your backup.

=== PostgreSQL

[source,bash]
----
# Create database and user
psql -U postgres -c "CREATE USER warmdesk WITH PASSWORD 'secret';"
psql -U postgres -c "CREATE DATABASE warmdesk OWNER warmdesk;"
----

[source,yaml]
----
db_driver: postgres
db_dsn: "host=localhost user=warmdesk password=secret \
  dbname=warmdesk"
# port=5432 sslmode=require
----

=== MySQL / MariaDB

[source,bash]
----
mysql -u root -p -e \
  "CREATE DATABASE warmdesk \
CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
mysql -u root -p -e \
  "CREATE USER 'warmdesk'@'localhost' IDENTIFIED BY 'secret';"
mysql -u root -p -e \
  "GRANT ALL PRIVILEGES ON warmdesk.* TO 'warmdesk'@'localhost';"
----

[source,yaml]
----
db_driver: mysql
db_dsn: "warmdesk:secret@tcp(localhost:3306)/warmdesk?charset=utf8mb4&parseTime=True&loc=Local"
----

IMPORTANT: `parseTime=True` is required — the server refuses to start without it. Without it, `DATETIME` columns fail to scan into Go's `time.Time`, so every read of a row with a timestamp column (which is nearly every table) silently fails, while writes keep working — this can surface as confusing, intermittent-looking "invalid credentials" or "not found" errors that have nothing to do with the actual data.

=== Database TLS

WARNING: If your database server is not on the same host as WarmDesk, enable TLS. Without it, all queries — including passwords and session data — travel in plaintext between the application and the database. Use `verify-full` in production; `disable` (the default) is only appropriate when the database socket is a local Unix socket or a loopback connection on the same machine.

Both PostgreSQL and MySQL support encrypted connections.
Use the `db_tls_*` settings (or their `DB_TLS_*` env var equivalents) instead of embedding TLS parameters in the DSN directly.

[cols="1,1,3", options="header"]
|===
|Setting |Env var |Description

|`db_tls_mode`
|`DB_TLS_MODE`
|`disable` (default) / `require` / `verify-ca` / `verify-full`

|`db_tls_ca_cert`
|`DB_TLS_CA_CERT`
|Path to CA certificate file

|`db_tls_cert`
|`DB_TLS_CERT`
|Path to client certificate (mTLS, optional)

|`db_tls_key`
|`DB_TLS_KEY`
|Path to client key (mTLS, optional)
|===

[source,yaml]
----
# Encrypt and fully verify the server certificate
db_tls_mode: "verify-full"
db_tls_ca_cert: "/etc/ssl/warmdesk/ca.pem"

# Additionally authenticate with a client certificate (mTLS)
db_tls_cert: "/etc/ssl/warmdesk/client.crt"
db_tls_key:  "/etc/ssl/warmdesk/client.key"
----

`require` encrypts the connection but skips certificate verification (useful for self-signed certs in development).
`verify-ca` checks the certificate chain; `verify-full` also checks that the hostname matches the certificate CN.

=== Schema migration

WarmDesk runs *GORM AutoMigrate* on every startup.
New columns and tables are created automatically; existing data is never destroyed.
There are no separate migration files to run.

== Running as a Service

=== systemd (Linux — recommended)

A ready-made unit file is at `deploy/warmdesk.service`.
Edit it before installing — at minimum set `JWT_SECRET` and `ALLOWED_ORIGINS`.

[source,ini]
----
[Service]
Environment="JWT_SECRET=your-secret-here"
Environment="ALLOWED_ORIGINS=https://warmdesk.example.com"
Environment="DB_DSN=/var/lib/warmdesk/warmdesk.db"
----

[source,bash]
----
sudo useradd -r -s /bin/false -d /opt/warmdesk warmdesk
sudo mkdir -p /opt/warmdesk/{data,uploads}
sudo cp -r dist/. /opt/warmdesk/
sudo chown -R warmdesk:warmdesk /opt/warmdesk

sudo cp deploy/warmdesk.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now warmdesk
sudo journalctl -u warmdesk -f   # follow logs
----

'''

== Reverse Proxy

Always run WarmDesk behind a reverse proxy in production.
Ready-made configs are in `deploy/`.

When the proxy runs on the same host as WarmDesk, set in `warmdesk.yaml`:

[source,yaml]
----
trusted_proxies: "127.0.0.1"
----

Both templates forward `X-Forwarded-For`; without `trusted_proxies`, auth logs and rate limiting record every client as `127.0.0.1`.

=== Nginx (`deploy/nginx.conf`)

The template in `deploy/nginx.conf` includes:

* A dedicated `location ~ ^/api/v1/ws` block with hardcoded `Upgrade: websocket` headers and 24-hour read/send timeouts (board updates, chat, video-call signalling)
* A separate `location /` block that does not forward upgrade headers (prevents h2c smuggling)
* `client_max_body_size 25m` to match WarmDesk's default `max_upload_mb`
* `X-Forwarded-For` and `X-Forwarded-Proto` on every proxied request

[source,bash]
----
sudo cp deploy/nginx.conf /etc/nginx/sites-available/warmdesk
# Edit: replace yourdomain.com and SSL certificate paths
sudo ln -s /etc/nginx/sites-available/warmdesk \
  /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
----

=== Apache (`deploy/apache.conf`)

[source,bash]
----
sudo a2enmod proxy proxy_http proxy_wstunnel ssl headers rewrite
sudo cp deploy/apache.conf \
  /etc/apache2/sites-available/warmdesk.conf
# Edit: replace yourdomain.com and SSL certificate paths
sudo a2ensite warmdesk
sudo systemctl reload apache2
----

The template uses vhost-level `ProxyPass /api/v1/ws ws://…` (before the catch-all `ProxyPass /`) with `ProxyTimeout 86400` so WebSocket connections stay alive for up to 24 hours.
It forwards `X-Forwarded-For`, `X-Real-IP`, and `X-Forwarded-Proto`.

=== Server TLS

WarmDesk can serve HTTPS directly without a reverse proxy.
Set both `tls_cert` and `tls_key` (or their `TLS_CERT` / `TLS_KEY` env vars) to enable it:

[source,yaml]
----
tls_cert: "/etc/ssl/warmdesk/server.crt"
tls_key:  "/etc/ssl/warmdesk/server.key"
----

When either value is absent the server starts in plain HTTP mode.
This is the right choice when TLS is terminated upstream by nginx, Apache, or a load balancer — no extra configuration is needed in that case.

NOTE: If you enable server TLS, update `ALLOWED_ORIGINS` and any reverse proxy config to use `https://` URLs accordingly.

=== CORS

Set `ALLOWED_ORIGINS` to the *exact* origin that users access WarmDesk from (including scheme and port).
A mismatch will prevent the frontend from making API calls.

[source,bash]
----
# Single domain
ALLOWED_ORIGINS=https://warmdesk.example.com

# Multiple domains (comma-separated)
ALLOWED_ORIGINS=https://warmdesk.example.com,\
https://warmdesk.internal

# Allow any origin (useful when the desktop app connects to an
# internal server that is not exposed to the internet)
ALLOWED_ORIGINS=*
----

Desktop app origins (`tauri://localhost`, `https://tauri.localhost`, `http://tauri.localhost`) are always allowed automatically regardless of this setting — no extra configuration is needed for the native clients.

== First Admin Account

Register normally through the web interface.
The *first account registered on a fresh database is automatically made a global admin* — no database manipulation required.

Once one admin exists, you can promote further users through *Admin → Users → Edit* in the web interface.

If public registration is not desired, disable it after creating the first admin: *Admin → Settings → Allow public registration → Off*.

TIP: If you ever need to promote an account via the database directly (e.g. after accidentally demoting the only admin), use the appropriate command for your database:

*SQLite*

[source,bash]
----
sqlite3 /var/lib/warmdesk/warmdesk.db \
  "UPDATE users SET global_role='admin' WHERE username='yourname';"
----

*PostgreSQL*

[source,sql]
----
UPDATE users SET global_role = 'admin' WHERE username = 'yourname';
----

*MySQL*

[source,bash]
----
mysql -u warmdesk -p warmdesk -e \
  "UPDATE users SET global_role='admin' \
WHERE username='yourname';"
----

*Global roles*

[cols="1,3", options="header"]
|===
|Role |Access

|`user`
|Can use the application; sees only their own projects

|`admin`
|Full access to all projects, all admin panel features

|`viewer`
|Read-only access; cannot create or modify anything

|`metrics`
|Can only call `GET /api/v1/metrics`; no access to any other endpoint

|`backup`
|Can only call `POST /api/v1/backup`; no access to any other endpoint

|`customer`
|Customer-portal access: can view and comment on tickets for assigned customers only; blocked from boards, chat, and time tracking
|===

The `metrics` role is intended for Prometheus scraper accounts.
Create a dedicated user with role `metrics`, then generate an API key for that user in *Admin → Users → (click user) → API Keys*.
Configure Prometheus to send `Authorization: ApiKey <key>` with each scrape request (see <<prometheus-metrics>> below).

The `backup` role is intended for automated backup scripts and cron jobs.
See <<backup-and-recovery>> for setup instructions.

The `customer` role is intended for end-customers who need a self-service portal to follow their own tickets.
Assign the user to one or more customers via *Admin → Users → (click user) → Customer Access*.
They can read all non-private messages and post replies, but cannot create, update, or delete tickets; cannot add tags, links, or apply macros; and cannot see internal (private) notes.

=== Login History

Every user has a *Login History* tab in the admin panel (*Admin → Users → (click user) → Login History*).
It records every authentication and security-sensitive action for that user, along with the IP address and client (User-Agent) of the request.

[cols="1,3", options="header"]
|===
|Event |When it is recorded

|`login_ok`
|Successful password or passkey login

|`login_failed`
|Failed login attempt (wrong password, unknown user, deactivated account, or failed passkey verification)

|`logout`
|Explicit logout

|`password_changed`
|User changed their own password

|`password_reset`
|Password reset completed via the emailed reset link

|`email_changed`
|User changed their email address

|`mfa_failed`
|A submitted MFA code was invalid, or the MFA session expired

|`mfa_ok`
|MFA challenge passed during login

|`mfa_challenge`
|An MFA challenge was issued after a successful password/passkey check

|`mfa_trusted_device`
|User elected to trust this device and skip MFA for 7 or 30 days

|`mfa_disabled`
|TOTP was disabled by the user

|`passkey_registered`
|WebAuthn passkey added

|`passkey_deleted`
|WebAuthn passkey removed

|`api_key_created`
|API key generated

|`api_key_deleted`
|API key revoked

|`admin_user_created`
|An admin created this account

|`admin_user_updated`
|An admin edited this user's profile or role

|`admin_user_deleted`
|An admin soft-deleted this user

|`admin_user_restored`
|An admin restored this user from soft-delete

|`admin_user_purged`
|An admin permanently deleted this user

|`admin_mfa_disabled`
|An admin reset this user's MFA

|`admin_passkeys_revoked`
|An admin revoked all of this user's registered passkeys
|===

NOTE: Enabling MFA is written to the server log but is *not* currently recorded as a Login History row — only `mfa_disabled` (self-service) and `admin_mfa_disabled` (admin reset) appear in the table above.

The *Performed by* column is blank for self-actions (the event was triggered by the user themselves).
For admin-on-behalf actions it shows the admin's username so you can tell apart a user changing their own password from an admin doing it for them.

=== Groups

Groups let you manage project and customer access for a set of users in one place instead of assigning each user individually.

[cols="1,3", options="header"]
|===
|Action |Where

|Create a group
|Admin → Groups → Create Group

|Edit name / description
|Admin → Groups → (click group)

|Add / remove members
|Admin → Groups → (click group) → Members tab

|Grant project access
|Admin → Groups → (click group) → Project Access tab

|Grant customer access
|Admin → Groups → (click group) → Customer Access tab

|Delete a group
|Admin → Groups → (click group) → Delete
|===

*How group access works*

Group access is *additive*: a user's effective role on a project or customer is the highest role they hold, whether that comes from a direct assignment or from any group they belong to.
Removing a user from a group immediately revokes any access they received exclusively through that group.

Global admins bypass all access checks and are unaffected by group assignments.

*Project roles via group*

[cols="1,3", options="header"]
|===
|Role |Effect

|`viewer`
|Read-only access to the project board and cards

|`member`
|Can create and edit cards, post comments

|`owner`
|Full project permissions including settings and member management
|===

*Customer roles via group*

[cols="1,3", options="header"]
|===
|Role |Effect

|`member`
|Can view the customer and its contracts

|`admin`
|Can edit the customer, create/edit contracts, manage members
|===

=== Customer access control

Non-admin users only see the customers they are *explicitly assigned to*.
A user with no customer assignments sees an empty customer list.

Assign customers in *Admin → Users → Edit User → Customer Access*.
Click a customer chip to toggle access; when a chip is selected, click the small *M* or *A* badge inside it to set the role:

[cols="1,3", options="header"]
|===
|Role |Access

|*M* (Member)
|Can see the customer and its contracts and projects

|*A* (Admin)
|All member permissions plus: edit customer details, create/edit contracts, manage the customer's member list
|===

Global admins bypass all customer access checks and always see every customer.

NOTE: The ticket *assignee* dropdown (Helpdesk) is populated only from *direct* Customer Access assignments, not group-based ones. If a customer's agents only have access via a Group, they can still view and work its tickets, but won't appear in the assignee dropdown — give each user who should be assignable a direct Customer Access row for that customer.

*Customer-admin self-service*

A user with the Admin role on a customer can also manage that customer's member list directly from the *Customer Detail* page → *Members* section, without needing access to the Admin panel.
They can add users, change roles, and remove members.
They cannot remove themselves from the customer (prevents self-lockout).

=== Prometheus metrics

`GET /api/v1/metrics` returns operational metrics in Prometheus text format.
Accessible to `admin` and `metrics` roles.

A ready-made Prometheus scrape config is in *`docs/prometheus.yml`*.
Minimal example:

[source,yaml]
----
scrape_configs:
  - job_name: warmdesk
    static_configs:
      - targets:
          - warmdesk.example.com
    metrics_path: /api/v1/metrics
    scheme: https
    authorization:
      type: ApiKey
      credentials: <your-api-key>
----

NOTE: `bearer_token` / `Authorization: Bearer` is reserved for JWT tokens and will not work here. Use `authorization.type: ApiKey` as shown above.

Metrics exposed:

[cols="1,1,3", options="header"]
|===
|Metric |Labels |Description

|`warmdesk_projects_total`
|—
|Active (non-archived) project count

|`warmdesk_columns_total`
|`project`, `project_name`
|Column count per project

|`warmdesk_cards_total`
|`project`, `column`, `status`
|Card count per column; `status` is `open` or `closed`

|`warmdesk_users_total`
|`role`, `active`
|User count per global role and active state (`true`/`false`)

|`warmdesk_customers_total`
|—
|Total number of customers

|`warmdesk_tickets_total`
|`status`
|Ticket count by status (`new`, `open`, `pending`, `pending_close`, `closed`)

|`warmdesk_tickets_by_priority_total`
|`priority`
|Open ticket count by priority (`low`, `medium`, `high`, `critical`)

|`warmdesk_sla_breaches_total`
|`type`
|Open tickets currently breaching SLA; `type` is `response` or `resolution`

|`warmdesk_ticket_messages_total`
|`visibility`
|Ticket message count; `visibility` is `public` or `private`

|`warmdesk_backup_last_run_timestamp_seconds`
|—
|Unix timestamp of last backup attempt (0 if never)

|`warmdesk_backup_last_success`
|—
|`1` = success, `0` = failed, `-1` = never run

|`warmdesk_backup_files_total`
|—
|Number of backup files currently stored
|===

==== Contracts

Each customer can have one or more contracts (*Customers → (click customer) → Contracts*).
A contract defines a billing period, a base hourly rate and currency, and optional time slots for standby or after-hours pricing.

To see a consolidated view of all standby time slots across every customer without clicking through each one, use the *Contract Rates* button in the Customers page header or in the Time Tracking toolbar.
The modal groups slots by customer → contract and shows from/to times, applicable days, and the rate or multiplier for each slot.

==== Standby time slots

Time slots let you define multiple rate windows on a contract — for example an evening/night rate or a weekend surcharge.
Each slot has:

[cols="1,3", options="header"]
|===
|Field |Description

|*Label*
|Free-text name, e.g. `Standby - week` or `Weekend surcharge`

|*From / To*

== Incoming Mail (IMAP)

WarmDesk can poll a mailbox and automatically create helpdesk tickets from incoming email.

=== Configuring the connection

Go to *Admin → Settings → Incoming Mail (IMAP)* and fill in:

[cols="1,3", options="header"]
|===
|Field |Notes

|*IMAP Host*
|Hostname of your mail server, e.g. `imap.gmail.com`

|*IMAP Port*
|Typically `993` (TLS)

|*Username*
|Mailbox username / email address

|*Password*
|Mailbox password or app-specific password

|*Authentication*
|`Plain` (username + password) or `OAuth2` (Google / Office 365)

|*Mailbox*
|Source folder to poll; default `INBOX`

|*Processed mailbox*
|Folder messages are moved to after a ticket is created; default `Processed`. The folder is created automatically if it does not exist.

|*Poll interval (seconds)*
|How often to check for new mail; default `60`
|===

Click *Test Connection* to verify the settings before saving.
Once saved, the poller starts automatically on next poll cycle.

=== Processed folder behaviour

After the poller picks up an email and creates a ticket, the message is *moved* from the source mailbox to the processed mailbox.
This prevents the same email from being turned into a duplicate ticket on the next poll.
The poller only ever reads from the source mailbox — emails in the processed folder are never re-scanned.

If the IMAP server does not support `MOVE` (RFC 6851), the message is marked `\Seen` in place instead.

TIP: If a user cannot find a message in their inbox, it was successfully processed and will be in the *Processed* folder.

=== OAuth2 authentication (Google and Office 365)

OAuth2 avoids storing a plain password and is required by providers that have disabled basic auth.

. Set *Authentication* to *OAuth2* and select the *Email Provider*.
. Click *Authorize* — a popup opens to the provider consent screen.
. Grant access. The popup closes and tokens are stored in the database.
. The poller refreshes the access token automatically before it expires.

Obtaining client credentials:

*Google (Gmail):*

. link:https://console.cloud.google.com/apis/credentials[Google Cloud Console] → Create project → OAuth consent screen (External, add scope `https://mail.google.com/`)
. Credentials → Create OAuth 2.0 Client ID → Web application → add Authorized Redirect URI: `https://your-domain/api/v1/admin/imap/oauth2/callback`
. Add the Client ID and Client Secret to `warmdesk.yaml`:

[source,yaml]
----
oauth2:
  google_client_id: "xxxx.apps.googleusercontent.com"
  google_client_secret: "GOCSPX-xxxx"
----

*Office 365 (Outlook):*

. link:https://portal.azure.com/#view/Microsoft_AAD_RegisteredApps[Azure Portal → App registrations] → New registration → Accounts in any organizational directory + personal Microsoft accounts
. Redirect URI: Web → `https://your-domain/api/v1/admin/imap/oauth2/callback`
. API permissions → Microsoft Graph → Delegated → `IMAP.AccessAsUser.All` + `offline_access`
. Add to `warmdesk.yaml`:

[source,yaml]
----
oauth2:
  office_client_id: "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
  office_client_secret: "xxxx~xxxx"
----

OAuth2 client credentials are read at startup — a restart is required after changing them in the YAML file.

== Horizontal Scaling

WarmDesk uses WebSocket connections for real-time updates.
In a single-instance setup, connections are managed in memory.
When running multiple instances behind a load balancer, each instance has its own connection pool — a message broadcast by one instance is not seen by clients connected to another.

=== Redis pub/sub

Enable Redis to route broadcasts across all instances:

[source,yaml]
----
redis_url: redis://localhost:6379
----

or

[source,bash]
----
REDIS_URL=redis://username:password@redis-host:6379/0
----

When `redis_url` is set, WarmDesk subscribes to a Redis channel and all `BroadcastToProject` calls publish to that channel.
Every instance receives the message and delivers it to its own connected clients.

=== Load balancer requirements

WebSocket connections require *sticky sessions* (a.k.a. session affinity) at the load balancer.
Without sticky sessions a client's HTTP upgrade request and subsequent WebSocket frames may reach different instances and fail.

With Redis enabled, sticky sessions are not strictly required for correctness, but they reduce Redis traffic.

=== Redis configuration

WarmDesk uses a single pub/sub channel per subscription scope.
A minimal Redis install with default settings works.
No persistence (AOF/RDB) is required for the pub/sub use case.

[source,bash]
----
# Test connectivity
redis-cli -h redis-host ping
----

== Backup and Recovery

=== What to back up

[cols="1,1,1", options="header"]
|===
|Item |Location |Frequency

|Database + uploads
|`./backups/` (via admin panel — bundles both by default)
|Daily or more

|Config
|`warmdesk.yaml`
|On change
|===

A backup created via the admin panel (or the `POST /api/v1/backup` endpoint) bundles the database dump together with `upload_dir` (attachments, avatars, customer logos, company branding) into a single archive, so restoring one brings everything back. Uncheck *Include uploaded files* in the scheduled-backup settings to go back to database-only backups if your upload directory is very large.

=== Via the Admin panel

The *Admin → Backup / Restore* tab provides full backup management without touching the server directly.

*Scheduled backups*

At the top of the tab you can configure automatic backups:

[cols="1,3", options="header"]
|===
|Field |Description

|*Interval*
|Disabled / Every 6 h (4×/day) / Every 8 h (3×/day) / Every 12 h (2×/day) / Once a day

|*Start time*
|Optional HH:MM anchor for slot-based scheduling (e.g. `02:00`). When set, backups run at fixed time-of-day slots derived from the start time and the chosen interval — for example, `02:00` + every 6 h produces runs at 02:00, 08:00, 14:00, and 20:00. Leave empty to use the default behaviour (interval counted from the last run).

|*Keep last (backups)*
|Maximum number of backup files to retain on disk. Oldest files are pruned automatically after each scheduled run. Default: 10.

|*Include uploaded files*
|When enabled (default), each backup bundles the upload directory (attachments, avatars, customer logos, company branding) together with the database. Disable this if your upload directory is very large and you only need database-only backups.
|===

The scheduler runs server-side — no cron job or external tool needed.
It checks every 5 minutes whether a backup is due and creates a new file when a slot has been missed.
The last run time and next scheduled run are displayed below the settings.

TIP: Set the start time to an off-peak hour (e.g. `02:00`) to ensure backups never run during business hours.

*Create a manual backup*

Click *Create Backup*.
WarmDesk creates a timestamped archive in `./backups/` next to the server binary:

[source]
----
./backups/warmdesk_backup_20260416_1430_a3f9.tar.gz
----

The filename format is `warmdesk_backup_YYYYMMDD_HHMM_<4-hex>.tar.gz`.
The four-character hex suffix is random and exists solely to prevent collisions when two backups are triggered within the same minute.
The archive contains the database dump under `db/` and, unless *Include uploaded files* is disabled, a copy of the upload directory under `uploads/`.

For SQLite, `VACUUM INTO` is used — an atomic online copy that requires no downtime.
For PostgreSQL, `pg_dump --clean --if-exists` is used.
For MySQL, `mysqldump` is used.

Backups created before this bundling was introduced (`warmdesk_db_YYYYMMDD_HHMM_<4-hex>.db`/`.sql`, database only) remain listable, downloadable, and restorable alongside the new format.

*List, restore, delete, and import backups*

All files in `./backups/` are listed in the tab with filename, size, and creation date, newest first.

* *Restore* — opens a dialog asking how to apply the backup:
** *Completely restart* — replaces the current database and uploaded files entirely with the backup's contents. All data added since the backup was made is lost. SQLite restores are live (the connection pool is closed, the file is replaced, and the connection is reopened — no server restart needed).
** *Add to current data* — merges the backup in instead of replacing anything. Uploaded files are copied in alongside existing ones (always safe — filenames are random and never collide). Database rows are inserted only when their ID doesn't already exist locally, and existing rows are never overwritten — SQLite only; for PostgreSQL/MySQL only the uploaded files are merged.
+
A confirmation prompt is shown before either option proceeds.
* *Download* — downloads the backup file directly to your browser. Useful for offsite storage or transferring backups to another server.
* *Delete* — removes the backup file from disk after confirmation.
* *Import Backup* — uploads a backup file from your computer (e.g. downloaded from another WarmDesk server) into `./backups/` so it can be restored or merged like any locally created backup. Accepts `.tar.gz`, `.db`, or `.sql`. Immediately after a successful import you're asked the same Completely restart / Add to current data question as above.

Every backup, restore, merge, and import operation is logged to the server log with the filename, database driver, user ID, and client IP.

TIP: *Add to current data* is the safe choice for bringing another team's or another server's data into an existing WarmDesk instance without wiping what's already there. Because two independently run servers have no shared ID space, a row whose ID happens to collide with an unrelated existing row is skipped rather than merged — check the response summary (tables/rows merged) after a merge to see what came across.

=== Automated backups (cron / CI)

Use the `backup` global role to create a service account for automated backups:

. In *Admin → Users*, create a user (e.g. `backup-bot`) and set their role to *Backup*.
. Log in as that user and generate an API key under *User Settings → API Keys*.
. Call `POST /api/v1/backup` on a schedule:

[source,bash]
----
# Cron — daily at 02:00
0 2 * * * curl -sf -X POST https://desk.example.com/api/v1/backup \
               -H "X-API-Key: cwk_your_key_here"
----

The `backup` role cannot access any other endpoint.

=== Server-side backup (manual)

You can also back up the database directly on the server without going through the API.

*SQLite*

[source,bash]
----
# Hot copy using VACUUM INTO — safe while the server is running
sqlite3 /var/lib/warmdesk/warmdesk.db \
  ".backup /backup/warmdesk-$(date +%Y%m%d).db"
----

*PostgreSQL*

[source,bash]
----
pg_dump -U warmdesk warmdesk \
  | gzip > /backup/warmdesk-$(date +%Y%m%d).sql.gz
----

*Restoring manually*

[source,bash]
----
# SQLite — stop the service, replace the file, restart
sudo systemctl stop warmdesk
cp /backup/warmdesk-20260416.db /var/lib/warmdesk/warmdesk.db
sudo systemctl start warmdesk

# PostgreSQL
gunzip -c /backup/warmdesk-20260416.sql.gz \
  | psql -U warmdesk warmdesk
----

=== Cross-driver restore (`warmdesk-db-convert`)

The restore options above (admin panel, manual dump/restore) all work only *within* the same database driver — a SQLite backup can only be restored onto a SQLite server, a PostgreSQL dump onto PostgreSQL, and so on. `warmdesk-db-convert`, shipped alongside `warmdesk` in the release tarball, fills the gap: it copies every table across *any* combination of the three supported drivers (SQLite, PostgreSQL, MySQL/MariaDB) — for example, restoring a production SQLite backup onto a MySQL-driven test server.

*Typical use: restore a backup onto a different server*

. Download or `scp` the backup file (`warmdesk_backup_*.tar.gz`, or a legacy bare `.db`/`.sql`) onto the destination server.
. From the destination server, in the directory where its `warmdesk.yaml` lives:
+
[source,bash]
----
./warmdesk-db-convert \
  --backup ~/warmdesk_backup_20260416_1430_a3f9.tar.gz \
  --dst-config ./warmdesk.yaml \
  --truncate
----

`--dst-config` reads `db_driver`, `db_dsn`, and `upload_dir` from that server's own config file — the same file (and environment-variable overrides) the app itself reads on startup — so the destination's database credentials never need to be typed on the command line. `--truncate` clears each destination table before importing, so the command can be re-run safely; omit it to add the backup's data on top of what's already there instead.

`--backup` handles the rest automatically:

* Extracts the archive and locates the database dump (`db/`) and, if bundled, the upload directory (`uploads/`).
* Detects which engine produced the dump — a real SQLite file is used directly as the source; a `pg_dump`/`mysqldump` `.sql` script is recognized from its standard header comment (including MariaDB's `mysqldump` build, which labels itself differently from Oracle's). If detection can't identify an unusual dump format, pass `--src-driver sqlite|postgres|mysql` to force it.
* A `.sql` script has no live database to read from, so restoring one requires `--src-dsn` pointing at an empty/scratch instance of that same engine (reachable from the machine running the conversion) to import the dump into first — this needs the matching `psql` or `mysql` client in `PATH`, the same tools the admin panel's own PostgreSQL/MySQL restore path already requires. Restoring a SQLite-sourced backup (the common case) needs none of this.
* Copies the bundled `uploads/` folder to `--dst-upload-dir` after the database is converted (filled in automatically from `--dst-config`, same as `db_driver`/`db_dsn`) — a full restore (database + attachments/avatars/logos) is one command with no manual `tar`/`rsync` step. If the backup bundles uploads but no destination is known, a note is logged rather than silently skipping them.

The destination schema is migrated automatically (the same `AutoMigrate` the server runs on every startup), so it can point at a brand-new, empty database.

*Converting directly between two running databases* (no backup file involved) works the same way with `--src-driver`/`--src-dsn` in place of `--backup`:

[source,bash]
----
./warmdesk-db-convert \
  --src-driver sqlite --src-dsn ./warmdesk.db \
  --dst-driver mysql  --dst-dsn "user:pass@tcp(host:3306)/warmdesk?charset=utf8mb4&parseTime=True&loc=Local"
----

TIP: Run `./warmdesk-db-convert` with no arguments for the full list of flags and usage notes.

== Migration Tools

`warmdesk-export` and `warmdesk-import` are standalone binaries (shipped in `dist/` alongside the main server) for moving projects between WarmDesk and other platforms.

[cols="1,2", options="header"]
|===
|Binary |Direction

|`warmdesk-export`
|WarmDesk → Jira, Trello, OpenProject, or Ryver

|`warmdesk-import`
|Jira, Trello, OpenProject, or Ryver → WarmDesk
|===

Both binaries export / import: columns, cards (with title, description, priority, start/due date, labels, tags, assignees, checklist, comments and their own attachments, time entries, attachments), and threaded topics. For Ryver specifically, `warmdesk-import` additionally imports the team's full chat history.

=== Configuration

Copy `warmdesk-migrate.yaml.example` to `warmdesk-migrate.yaml` and fill in the connection details.
Sensitive values can be supplied as environment variables instead:

[source]
----
WARMDESK_URL        URL of your WarmDesk instance
WARMDESK_USERNAME   WarmDesk account username
WARMDESK_PASSWORD   WarmDesk account password
WARMDESK_PROJECT    Project slug (visible in the URL; warmdesk-export only)
PLATFORM_API_TOKEN  API token for the target platform
PLATFORM_API_KEY    API key for the target platform (Trello)
----

Any field still missing after reading the file and environment is prompted interactively.

`warmdesk-import` always creates a **new** project, named after the source project/team — it never writes into an existing one. Every WarmDesk project needs a customer, so `warmdesk.customer` (the exact name of an existing customer) is required; resolving it, along with resolving `user_map` usernames below, requires the `warmdesk.username` account to be a global admin. `warmdesk.key_prefix` optionally overrides the auto-derived card prefix (the first three letters of the project name), for when two source projects would otherwise collide on it.

=== Column mapping

The `column_map` section in the config translates WarmDesk column names to the corresponding status / list names on the target platform (and back on import):

[source,yaml]
----
column_map:
  Backlog: "To Do"
  "In Progress": "In Progress"
  "Test & Review": "In Review"
  "To Production": Done
----

Columns not listed are passed through unchanged.

=== User mapping

The `user_map` section maps an external display name (as it appears on a card, comment, or chat message) to a WarmDesk username, so `warmdesk-import` assigns cards to, and attributes comments/messages to, the right person instead of everything landing on the importing account:

[source,yaml]
----
user_map:
  "Jane Doe": jane
  "jane.d": jane   # a second external name (e.g. a bare username) can map to the same account
----

Author attribution works by minting a short-lived personal API key for the mapped WarmDesk account (the same mechanism as Admin → Users → API Keys), posting as that user, then revoking the key — so imported comments and chat messages are genuinely authored by the right person, not just labeled with their name. A name not listed here is imported unassigned (cards) or with a `*[Name]* ...` text prefix instead of real authorship (comments/messages).

=== Content selection (Ryver only)

The `include` section controls which categories of content `warmdesk-import` pulls from Ryver. Both default to `true` (import everything) when the section, or a field within it, is omitted — existing config files need no changes:

[source,yaml]
----
include:
  cards: true   # columns, cards, topics
  chat: true    # team/group chat history
----

This is useful for importing cards and chat history as separate runs, or re-running one without repeating the other.

=== Usage

[source,bash]
----
cd dist

# Export a WarmDesk project to Jira
./warmdesk-export --config warmdesk-migrate.yaml

# Import a Jira project into WarmDesk
./warmdesk-import --config warmdesk-migrate.yaml

# Preview what would happen without making any changes
./warmdesk-export --dry-run
./warmdesk-import --dry-run
----

== Security Checklist

Before exposing WarmDesk to the internet:

* [ ] Changed `JWT_SECRET` to a randomly generated 32-byte hex string
* [ ] Set `ALLOWED_ORIGINS` to the exact production domain
* [ ] Running behind HTTPS (TLS termination at the reverse proxy)
* [ ] `GIN_MODE=release` (suppresses debug output)
* [ ] `API_LOG=false` (or piped to a log file, not stdout)
* [ ] Database credentials are strong and not the defaults
* [ ] Uploads directory (`upload_dir`) is outside the web root
* [ ] Firewall allows inbound traffic on port 80/443 only; WarmDesk's port (8080) is not directly exposed
* [ ] Systemd service runs as a non-root dedicated user (`warmdesk`)
* [ ] Backup schedule is in place for the database and uploads
* [ ] Public registration disabled (*Allow public registration = off*) if only known users should access the instance
* [ ] Password policy configured (*Admin → Settings → Password Policy*) with a minimum length of at least 12 and one or more character-class requirements
* [ ] SMTP credentials (if used) are an app-specific password, not a primary account password
