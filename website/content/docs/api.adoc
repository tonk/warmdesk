== Interactive API (Swagger UI)

WarmDesk ships with a full Swagger UI at:

----
http://<your-server>:8080/swagger/index.html
----

The interactive documentation lists every endpoint, shows request/response schemas, and lets you try requests directly from the browser.
Enter a valid JWT Bearer token via the *Authorize* button to authenticate requests.

== Authentication

=== JWT (user sessions)

Obtain an access token:

[source,bash]
----
curl -s -X POST https://warmdesk.example.com/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"hunter2"}' \
  | jq .access_token
----

Use the token in subsequent requests:

[source,bash]
----
curl -H "Authorization: Bearer <token>" \
     https://warmdesk.example.com/api/v1/projects
----

* Access tokens expire after *15 minutes*
* The frontend silently refreshes using the 7-day refresh token
* A 401 response from the API signals an expired token

=== API keys

API keys authenticate CI/CD pipelines and automation scripts.
Create a personal API key in *Settings → API Keys* (full access as you, across all your projects), or a project-scoped key in *Project Settings → API Keys* (locked to that one project).

Send the key in either header:

* `X-API-Key: <key>`
* `Authorization: ApiKey <key>` — for tools that can only set the `Authorization` header (e.g. Prometheus)

[source,bash]
----
curl -H "X-API-Key: cwk_abc123..." \
     https://warmdesk.example.com/api/v1/projects
----

API keys carry the same project permissions as the user who created them, and work on all authenticated endpoints, not just the Ticket API.
A project-scoped key only works on routes that contain its own project's slug (e.g. `/api/v1/projects/{slug}/...` or `/api/v1/ticket/{slug}/...`); anything else returns `key is scoped to a specific project`.
Keys with the `backup` global role can trigger backups without a full admin account.

== Ticket API

The Ticket API is designed for CI/CD automation and external tools.
All endpoints live under `/api/v1/ticket/{projectSlug}/` and use `X-API-Key` authentication.
The `GET` endpoints need only viewer access and never change anything; the others need member access (commenting needs viewer access).

[cols="1,3,3",options="header"]
|===
|Method |Path |Action
|`GET` |`/api/v1/ticket/{slug}/columns` |List columns (lanes), left to right
|`GET` |`/api/v1/ticket/{slug}/cards` |List cards
|`GET` |`/api/v1/ticket/{slug}/cards/{cardId}` |Get one card, with its comments
|`POST` |`/api/v1/ticket/{slug}/cards` |Create a card
|`POST` |`/api/v1/ticket/{slug}/cards/{cardId}/comments` |Add a comment
|`PATCH` |`/api/v1/ticket/{slug}/cards/{cardId}/move` |Move a card to another column
|===

=== Read a lane

`GET /cards` returns open cards ordered by column, then position.
Each card includes `column_name` and its `key` (e.g. `ANSI-12`), plus `priority`, `story_points`, `time_spent_minutes`, `due_date`, labels, tags, assignees, and epic.

[cols="1,1,4",options="header"]
|===
|Query parameter |Type |Notes
|`column` |string |Only cards in the column with this name (case-insensitive), e.g. `Backlog`
|`column_id` |number |Only cards in this column
|`include_closed` |bool |`true` to also return closed cards
|===

An unknown column returns `400 column not found in project`.

[source,bash]
----
curl -s -H "X-API-Key: cwk_abc123..." \
  "https://warmdesk.example.com/api/v1/ticket/myproject/cards?column=Backlog" \
  | jq '.[] | {key, title, priority, story_points}'
----

=== Create a card

Look up the target `column_id` with `GET /columns` first.
`priority` is not accepted here; new cards get the default (`none`).

[source,bash]
----
curl -X POST \
  -H "X-API-Key: cwk_abc123..." \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Security scan found CVE-2026-1234",
    "description": "**Severity:** High\n\nFound in dependency `foo@1.2.3`.",
    "column_id": 5
  }' \
  "https://warmdesk.example.com/api/v1/ticket/myproject/cards"
----

Returns `201 Created` with the new card.

=== Add a comment / move a card

`{cardId}` is the card's numeric `id` from the create/list response, not its `key`.

[source,bash]
----
# Add a comment
curl -X POST \
  -H "X-API-Key: cwk_abc123..." \
  -H "Content-Type: application/json" \
  -d '{"body": "Deployment to production succeeded. Build #4242."}' \
  "https://warmdesk.example.com/api/v1/ticket/myproject/cards/42/comments"

# Move the card to column 8 (omit position to append at the end)
curl -X PATCH \
  -H "X-API-Key: cwk_abc123..." \
  -H "Content-Type: application/json" \
  -d '{"column_id": 8}' \
  "https://warmdesk.example.com/api/v1/ticket/myproject/cards/42/move"
----

== Webhooks

=== Generic webhook (chat notifications)

Post any JSON payload to push a message to a project's chat channel:

[source,bash]
----
curl -X POST \
  -H "Content-Type: application/json" \
  -d '{"text":"Deployment to staging succeeded 🚀","username":"CI"}' \
  "https://warmdesk.example.com/api/v1/webhooks/<token>"
----

The token is generated in *Project Settings → Webhooks*.

=== Git platform webhooks

Register an endpoint in your git host's project settings to link commits and pull requests to cards.
Card references in commit messages and PR titles (`PROJ-42`) are parsed automatically.

[source]
----
POST /api/v1/github-webhook/:token    # GitHub push, PR, issue events
POST /api/v1/gitlab-webhook/:token    # GitLab push, MR, issue events
POST /api/v1/gitea-webhook/:token     # Gitea / Forgejo push, PR, issue events
----

== Response format

All success responses return JSON.
All error responses use a consistent shape:

[source,json]
----
{ "error": "human readable message" }
----

HTTP status codes follow standard conventions:

[cols="1,2"]
|===
|200 |OK — resource returned or updated
|201 |Created — resource created; `id` in response
|204 |No Content — successful delete
|400 |Bad Request — validation error
|401 |Unauthorized — missing or expired token
|403 |Forbidden — insufficient role
|404 |Not Found — resource does not exist or is not accessible
|422 |Unprocessable Entity — semantic validation error
|500 |Internal Server Error — server-side bug
|===

== WebSocket

=== Project WebSocket

[source]
----
wss://warmdesk.example.com/api/v1/ws/:projectSlug?token=<jwt>
----

Messages are JSON objects `{"type": "...", "payload": {...}}`.

Common event types:

[cols="1,2"]
|===
|`board.card_created` | A card was created in the project
|`board.card_updated` | A card field was changed
|`board.card_moved`   | A card was moved to another column
|`board.card_deleted` | A card was soft-deleted
|`chat.message`       | A new chat message was posted
|`topic.created`      | A new topic was created
|`presence.join`      | A user opened the project
|`presence.leave`     | A user left the project
|===

=== User WebSocket

[source]
----
wss://warmdesk.example.com/api/v1/ws/user?token=<jwt>
----

Delivers user-level events: DM messages, @mentions, and card notifications.

== Prometheus metrics

[source]
----
GET /api/v1/metrics
----

Requires `Authorization: Bearer <token>` with the `metrics` or `admin` global role.
Returns standard Prometheus text format.
